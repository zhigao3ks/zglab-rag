# 企业 AI 合同审查 · 脱敏项目知识卡

> 本文是从真实企业项目中抽取的公开安全版本，仅保留技术架构、工程逻辑与可复用经验。公司名称、内部地址、数据库 Schema、真实合同规则、业务账号、内部接口路径和其他敏感标识均已删除或泛化。

## 项目定位

该项目面向企业合同审查场景，希望把 Word 合同解析、合同类型识别、确定性规则校验、LLM 语义审查、结果聚合、问题定位和 HTML 报告生成组织成一套可扩展的审查平台。

系统不是让一个大模型直接“读完整合同并自由判断”，而是把流程拆成：

```text
文件接收
  ↓
统一解析
  ↓
合同类型识别
  ↓
公共规则
  ↓
专项审查
  ↓
结果聚合
  ↓
质量控制
  ↓
持久化 / 归档
  ↓
HTML 报告与问题定位
```

其中确定性程序负责结构、格式、数值、日期、表格和强约束检查；LLM 主要负责条款语义、上下文一致性、风险表达和难以形式化的判断。

## 技术栈

后端主要采用：

- Python 3.12；
- Web API 框架；
- Pydantic / 结构化数据模型；
- 关系型数据库；
- Word 文档解析和 HTML 渲染；
- LLM API；
- 配置驱动的专项注册机制。

前端主要采用：

- Vue 3；
- TypeScript；
- Vite；
- 文档预览；
- 问题列表与锚点定位。

输入以 Word 合同为主，旧格式文档会先转换为统一可解析格式，再进入后续流程。

## 核心设计原则：只解析一次

不同合同专项不能各自重复解析 Word。

公共层先将原始合同转换为统一的 `StructuredDocument`，后续分类、规则、LLM 和报告全部复用这一结构化结果。

这样做可以：

- 避免重复解析造成性能浪费；
- 避免不同专项得到不同文本结构；
- 为表格、段落、章节、锚点提供统一编号；
- 方便问题定位和 HTML 高亮；
- 让新增专项只关注审查逻辑。

## 公共流程与专项流程分离

公共任务服务只负责稳定的公共阶段：

```text
Upload
→ Parse
→ Classify
→ Common Rules
→ Dispatch Specialist
→ Aggregate
→ Persist
→ Archive
→ Report
```

合同专项则通过注册表动态加载。

新增一个专项原则上只需要：

```text
专项实现模块
+ 专项规则配置
+ 专项测试
+ 一条注册配置
```

不应该修改公共任务主流程，也不应该在公共调度器中不断增加：

```python
if contract_type == ...
```

这种硬编码分支。

## 专项统一协议

不同合同类型内部实现可以不同，但对公共层暴露统一协议。

抽象形式类似：

```python
def review_contract(
    document,
    *,
    business_context,
    interface_code,
    interface_version,
    rule_version,
) -> ContractReviewResult:
    ...
```

统一结果至少需要表达：

- 审查是否完整；
- 风险 / 问题列表；
- 证据和定位信息；
- 警告；
- 结构化错误；
- 模型调用统计；
- 中间质量信息。

这样公共持久化、前端展示和报告生成就不需要理解每个专项的内部实现。

## 多种专项实现路线

项目实践中没有强行把所有合同做成完全相同的审查流程，而是允许多种方案共存。

### 路线 A：章节化 LLM 审查

适合结构相对稳定、规则比较完整的合同。

流程可以抽象为：

```text
合同章节划分
  ↓
章节并发审查
  ↓
章节结果聚合
  ↓
跨章节一致性检查
  ↓
全局质量评估
  ↓
必要时有限次数定向重审
```

优点是上下文更聚焦，模型不会一次处理过长合同。

### 路线 B：确定性规则 + 分组语义审查

适合包含大量表格、金额、日期、附件或固定业务字段的合同。

先由代码完成：

- 必填项；
- 日期格式；
- 数值关系；
- 表格列映射；
- 附件存在性；
- 字段之间的确定性一致性。

再把需要语义判断的条款按上下文分组交给 LLM。

### 路线 C：配置驱动 detector + LLM

将部分规则定义为配置化 detector，由确定性引擎先筛选候选问题，再结合上下文进行语义复核。

这种方式适合不断增加合同类型时降低重复开发成本。

## Rules Are Not Prompts

项目中一个重要原则是：

> 能明确写成代码的规则，不应该让 LLM 猜。

例如：

- 金额计算；
- 日期是否合法；
- 表格是否缺列；
- 字段是否存在；
- 必填附件是否存在；
- 固定枚举是否合法。

这些问题由程序判断更加稳定、便宜、可测试。

LLM 更适合：

- 条款语义；
- 权利义务是否失衡；
- 不同章节是否冲突；
- 风险描述；
- 隐含条件；
- 复杂上下文理解。

这种“确定性外层 + LLM 语义能力”的组合比把全部规则写进一个巨大 Prompt 更可靠。

## 分类与路由

系统提供两种入口。

### 自动识别

```text
上传合同
  ↓
提取结构化特征
  ↓
识别合同类型
  ↓
选择已注册专项
  ↓
执行专项审查
```

### 手动选择

用户也可以显式选择合同类型，用于业务确认、测试和分类不确定时的兜底。

前端合同类型列表从服务端动态获取，而不是在页面中维护一份重复映射。

## 审查结果与失败降级

专项内部可能包含多个规则批次和多个模型调用，因此不能把一次模型失败简单等价为整个任务失败。

系统采用部分结果保留策略：

```text
已验证的问题
    ↓ 保留
某个语义批次失败
    ↓
记录 warning / error
    ↓
返回 partial / degraded 状态
```

已经经过确定性验证或成功模型调用得到的结果不会因为后续某一步失败而全部丢弃。

这种机制比“一处异常整个合同返回 500”更适合长链路 AI 任务。

## 模型调用可观测性

每次模型调用都应被转换为统一的 usage 记录，包括：

- 所属审查阶段；
- Token；
- 耗时；
- 成功 / 失败状态；
- 请求标识；
- 对应章节或上下文组。

任务层再聚合：

```text
总调用次数
总 Token
总耗时
总体状态
```

这样才能真正分析成本、延迟和不同专项方案的效果。

## 前端产品流程

前端被拆成三个主要场景：

```text
自动识别
手动选择
结果查看
```

### 自动识别页面

用户上传 Word，系统自动判断合同类型并执行对应专项。

### 手动选择页面

用户先选择合同类型，再上传合同，直接进入指定专项。

### 结果工作区

结果页采用文档和问题的联动设计：

```text
合同 HTML 预览   |   风险问题列表
                 |
点击问题 --------+--> 定位原文
```

后端在 Word → HTML 时为段落、表格或单元格生成稳定锚点。

问题结果携带：

```text
anchor_id
quote_text
issue metadata
```

前端优先按锚点定位，失败时再通过引用文本做近似匹配，并滚动、高亮相关区域。

## 任务归档

每次审查使用唯一 task id，并保留必要产物。

典型归档包括：

- 原始合同；
- 结构化解析结果；
- 中间审查结果；
- 最终问题列表；
- HTML 预览；
- 完整审查报告；
- 任务日志和模型调用统计。

数据库负责保存可查询的任务、问题、产物和模型调用元数据，大文本或 HTML 等文件型产物则通过独立归档管理。

真实模型密钥不进入数据库和任务产物。

## 企业系统集成

AI 合同审查能力可以作为企业 OA 或流程系统的独立智能服务。

外部系统主要需要三个方向的接口：

```text
发起审查
查询最新结果
回写人工反馈
```

这种集成方式让 AI 服务保持自己的任务生命周期，同时允许企业原系统继续作为最终业务入口。

公开设计不记录内部 OA 路由、数据库字段或企业专有流程。

## 项目中的关键工程经验

### 1. 大模型不是规则引擎

确定性约束越多，越应该代码化，否则结果不稳定且难测试。

### 2. Context Engineering 比“整篇合同塞给模型”更重要

通过章节、上下文组和结构化数据缩小模型看到的信息范围，可以同时改善准确率、成本和延迟。

### 3. 公共框架应该稳定，专项应该可插拔

当合同类型持续增长时，主流程不能随着类型数量线性膨胀。

### 4. AI 长链路必须支持部分失败

确定性检查、多个语义批次、质量检查和报告生成之间需要清晰的失败边界。

### 5. 结果必须能够回到原文

只有“风险描述”而没有原文证据和定位，会严重降低法务或业务人员的使用效率。

### 6. 成本需要成为一等指标

模型调用次数、Token、延迟和重审次数必须可观测，才能做真正的工程优化。
